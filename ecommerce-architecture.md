# Архитектура интернет-магазина

Для текущего проекта рекомендуется архитектура **«модульный монолит»**: один Laravel-проект, одна база данных, Livewire для интерактивного интерфейса и отдельные модули по бизнес-задачам.

Документ исходит из того, что создаётся один интернет-магазин с несколькими сотрудниками, а не маркетплейс с независимыми продавцами.

## Общая схема

```text
Покупатель
    ↓
Blade + Livewire + Tailwind
    ↓
Livewire Pages / Controllers
    ↓
Actions — бизнес-операции
    ↓
Eloquent Models
    ↓
PostgreSQL / MySQL

Дополнительно:
Redis → кеш, очереди, блокировки
Storage/S3 → изображения товаров
PaymentGateway → платёжная система
DeliveryProvider → служба доставки
```

Текущий стек уже подходит:

- Laravel 13;
- PHP 8.5;
- Livewire 4;
- Flux UI 2;
- Tailwind CSS 4;
- Fortify для авторизации, 2FA и passkeys;
- Pest для тестирования.

React, Vue и отдельный API для первой версии не нужны.

## Функциональные модули

### 1. Catalog

Отвечает за:

- товары;
- категории;
- бренды;
- варианты товаров;
- характеристики;
- изображения;
- цены;
- публикацию товаров;
- фильтрацию и поиск.

Основные модели:

```text
Category
Brand
Product
ProductVariant
ProductMedia
Attribute
AttributeValue
```

`Product` хранит общее описание товара, а `ProductVariant` — конкретный продаваемый вариант: размер, цвет, SKU, цена и остаток.

Например:

```text
Product: Футболка
    ├── Variant: белая / S / SKU-001
    ├── Variant: белая / M / SKU-002
    └── Variant: чёрная / M / SKU-003
```

### 2. Inventory

Управление остатками должно быть отделено от каталога:

```text
inventories
- product_variant_id
- available_quantity
- reserved_quantity
```

Дополнительно желательно иметь `inventory_movements` — историю поступлений, продаж, возвратов и ручных корректировок.

Остатки необходимо изменять транзакционно с блокировкой строки. Иначе два покупателя смогут одновременно приобрести последнюю единицу товара.

### 3. Cart

Модели:

```text
Cart
CartItem
```

Корзина должна поддерживать:

- авторизованного пользователя;
- гостя через случайный токен;
- объединение гостевой корзины с пользовательской после входа;
- изменение количества;
- удаление недоступных позиций.

Цена из браузера никогда не принимается. При отображении и оформлении корзины сервер повторно получает цену из каталога.

Товар в корзине не резервируется. Резерв создаётся только при оформлении заказа.

### 4. Checkout

Checkout — отдельный процесс, а не большой метод в Livewire-компоненте.

Основные операции:

```text
CalculateCartTotals
ValidateCart
PlaceOrder
ReserveInventory
CreatePayment
```

`PlaceOrder` выполняется внутри транзакции:

1. Повторно загружает товары и цены.
2. Проверяет доступность вариантов.
3. Рассчитывает скидку и доставку.
4. Создаёт заказ.
5. Копирует данные товаров в позиции заказа.
6. Резервирует остатки.
7. Создаёт платёжную попытку.

### 5. Orders

Модели:

```text
Order
OrderItem
OrderAddress
OrderStatusHistory
```

В `OrderItem` нужно сохранять снимок товара:

- название;
- SKU;
- выбранные характеристики;
- цену за единицу;
- количество;
- сумму.

Нельзя показывать историю заказа только через текущий `Product`: товар может быть переименован, подорожать или удалиться.

Деньги нужно хранить целыми числами в минимальных денежных единицах:

```text
129900 = 1 299,00 ₽
```

Для денег нельзя использовать `float`.

Статусы лучше разделить:

```text
OrderStatus:
- Pending
- Confirmed
- Completed
- Cancelled

PaymentStatus:
- Pending
- Paid
- Failed
- PartiallyRefunded
- Refunded

FulfillmentStatus:
- Unfulfilled
- Processing
- Shipped
- Delivered
- Returned
```

Так заказ может быть одновременно оплачен, но ещё не отправлен.

### 6. Payments

Внешняя платёжная система должна подключаться через контракт:

```text
PaymentGateway
    ├── YooKassaGateway
    ├── StripeGateway
    └── FakePaymentGateway
```

Модели:

```text
Payment
PaymentTransaction
Refund
```

Критически важные правила:

- успешный возврат пользователя на сайт не подтверждает оплату;
- оплату подтверждает только подписанный webhook;
- webhook должен быть идемпотентным;
- идентификатор операции провайдера должен иметь уникальный индекс;
- обработка платежа и изменение заказа выполняются транзакционно.

### 7. Delivery

Контракт:

```text
DeliveryProvider
```

Модели:

```text
ShippingMethod
Shipment
```

Для MVP можно начать с фиксированных способов доставки. Интеграцию с внешними службами можно добавить позже, не меняя оформление заказа.

### 8. Promotions

После основного checkout можно добавить:

```text
Promotion
Coupon
CouponUsage
```

Расчёт скидки должен находиться в отдельном `CalculateDiscounts`, а итог применённой скидки сохраняться в заказе.

### 9. Customers

Используется существующий `User` и Fortify:

- регистрация;
- вход;
- восстановление пароля;
- подтверждение email;
- 2FA;
- passkeys.

Дополнительные модели:

```text
CustomerAddress
Wishlist
Review
```

Гостевое оформление лучше разрешить: у заказа `user_id` может быть `null`, но email и контактные данные обязательны.

## Команда и административная панель

Существующую модель `Team` стоит использовать как группу сотрудников магазина:

```text
Owner
Admin
Member
```

Позже роли можно уточнить:

```text
Owner
Administrator
CatalogManager
OrderManager
Support
```

Права должны проверяться через policies, а не условиями внутри шаблонов.

Для одного магазина добавлять `team_id` во все товары и заказы не нужно. Если цель изменится на SaaS, где каждая команда управляет собственным магазином, тогда понадобится отдельная сущность `Store` и tenant-scoping по `store_id`.

## Структура приложения

Не стоит сразу создавать сложный `Domain`-слой или Repository для каждой модели. Для этого проекта достаточно стандартной Laravel-структуры:

```text
app/
├── Actions/
│   ├── Cart/
│   ├── Catalog/
│   ├── Checkout/
│   ├── Inventory/
│   ├── Orders/
│   └── Payments/
├── Contracts/
│   ├── PaymentGateway.php
│   └── DeliveryProvider.php
├── Data/
├── Enums/
├── Events/
├── Jobs/
├── Listeners/
├── Models/
├── Notifications/
├── Policies/
└── Http/
    └── Controllers/
        └── Webhooks/

resources/views/
├── pages/
│   ├── shop/
│   ├── account/
│   └── admin/
└── components/
    ├── product-card.blade.php
    ├── money.blade.php
    └── shop/
```

Бизнес-логика живёт в Actions, связи и простые запросы — в моделях, состояние интерфейса — в Livewire-компонентах.

## Страницы

### Публичная витрина

```text
/
/catalog
/catalog/{category}
/products/{product:slug}
/cart
/checkout
/orders/{order:number}/success
```

### Личный кабинет

```text
/account/orders
/account/orders/{order:number}
/settings/profile
/settings/security
```

### Административная часть

```text
/{current_team}/admin
/{current_team}/admin/products
/{current_team}/admin/categories
/{current_team}/admin/orders
/{current_team}/admin/inventory
/{current_team}/admin/customers
/{current_team}/admin/promotions
/{current_team}/admin/settings
```

Публичную витрину лучше сделать серверно отображаемой для SEO. Livewire использовать для фильтров, корзины, checkout и административных форм. Flux UI хорошо подходит для админки, а витрине лучше дать собственный дизайн на Blade и Tailwind.

## События и очереди

Доменные события:

```text
OrderPlaced
PaymentSucceeded
PaymentFailed
OrderCancelled
OrderShipped
InventoryLow
```

В очереди отправляются:

- письма;
- уведомления;
- обработка изображений;
- синхронизация с доставкой;
- обновление поискового индекса;
- освобождение просроченных резервов.

Критические изменения заказа и остатков выполняются синхронно в транзакции. Уведомления запускаются после успешного commit.

## Инфраструктура

Для разработки текущий SQLite подойдёт. Для production:

- PostgreSQL или MySQL;
- Redis для очередей, кеша и атомарных блокировок;
- S3-совместимое хранилище для изображений;
- планировщик Laravel для просроченных заказов и резервов;
- queue worker;
- резервное копирование базы и файлов.

Полнотекстовый поисковый сервис на старте не нужен. Сначала достаточно поиска и фильтров средствами базы данных с правильными индексами.

## Этапы реализации

1. Категории, товары, варианты, изображения и административный CRUD.
2. Публичный каталог, карточка товара, фильтры и SEO.
3. Корзина и гостевой пользователь.
4. Checkout, заказы и резервирование остатков.
5. Оплата через webhook.
6. Доставка и уведомления.
7. Купоны, избранное и отзывы.
8. Кеширование, аналитика и расширенный поиск.

## Главный архитектурный принцип

Не нужно заранее строить микросервисы и универсальную платформу. Текущий Laravel-проект должен оставаться модульным монолитом, а контракты нужны только на внешних границах — платежи, доставка и другие интеграции.
